OD 检测任务的 Reformulation

讨论历程 · 从实现层被拉回计算理论层

这次 reformulation 的价值一半在结论、一半在"怎么纠偏"。完整保留走过的弯路。

起点 · 窄任务 grid sparse-OD
单类 Vehicle 的 grid sparse-OD 想扩到行人/骑行——它们小、且扎堆，加密 grid 后 dense decoder 算力爆炸。缩检测范围治标不治本（骑行移动快、不能缩距离）。
弯路 · 主 Agent 一头扎进实现层 L3L2
上来就谈"两段式门控 / 复用 exist 做 gate / 冻结 ckpt 离线证伪 / 省算力-召回曲线 / top-K vs score-mask / TRT"——全是算法层与实现层的机制。用户纠偏 ①"train 一定是 sparse 的"（不能在 dense ckpt 上推理期证伪 formulation）②"召回代价这些已经在实现层"。
纠偏 · 以 Marr 视角重来 L1
放弃机制执念，上到计算理论层：先回答"驾驶感知/检测到底要算什么、为什么、有哪些天然约束"。并把这套纪律蒸馏成 marr-levels skill：任何算法讨论 Step 0 先定 L1/L2/L3，防止层级坍缩。
L1 收敛 · 用户给 OD 划边界
OD = 检测所有可见物体（可见即在 scope、可交互；完全遮挡=出 scope）；意图归 e2e、交互归 eval 专门 metric、occupancy/stuff 另属任务。主 Agent 一度把"无上限基数/必须捞回每个"的 imposed L1 扣上去，被用户纠正：基数由可见性/分辨率封顶。
方案定稿 · 用户 proposal L2L3
per-view Perceiver mono3d（存在→geo、adaptive compress = topk+group）→ 跨 view SA → 定长 N 个 BEV unified token 去重关联 + 时序传播 → 与 lidar/radar SA。轻量、可升级 e2e。
01

Marr 三层分析 · 讨论纪律

蒸馏自 David Marr《Vision》(1982)。最致命的误读：把 L1 的 "computational" 当成"怎么算/算力/算子"——那是 L3。L1 是问题的理论，不是解法。

L1 计算理论

要算的是什么、为什么、哪些天然约束使问题良定义。

  • 例：感知为行动服务，恢复"可见物体实例集"
  • Marr：只看机制看不清问题，"像研究羽毛理解飞行"

L2 表征与算法

用什么表征 + 什么算法实现 L1。

  • 框 / 占用 / query / token
  • 匈牙利 / 门控 / Perceiver / SA / slot

L3 实现

如何在硬件上物理实现。

  • CUDA 算子 / 稀疏 kernel / 显存
  • TRT / 定长静态 shape
纪律：只有上一层谈拢，才允许下沉一层

在 L1 就只谈目标/为什么/输出本体/天然约束，把表征、算法、算力全挡在门外；发现层级坍缩（用机制冒充目标、用算力冒充计算理论）当场点名、抬回正确层级。

02

OD 的 L1 · 计算理论

从用户 proposal 反读出的 OD 计算理论（不臆测、以用户划的边界为准）。

🎯 目标 & 范围

  • 恢复所有可见物体实例：ego/BEV 帧下统一、时序持存的实例集。
  • 可见=in-scope=必检；完全遮挡=不可交互=出 scope。可见性本身即"可度量、自然"的 relevance 判据。
  • 基数由可见性/分辨率封顶——一视图可分辨个体有限，固定但足量的 query 预算是有原理的。

🧭 边界（划给别人的）

  • 意图/行为 → 是 L1 输出没错，但归 e2e，非 OD。
  • 交互 → 非 OD 核心，放到 evaluation 专门 metric，不进核心 loss。
  • occupancy / stuff（地面/墙）→ 另属任务；OD 只管 thing / instance 这一侧。

⚙️ 因子分解 · 存在→geo（what→where）

存在/类别是召回关键、便宜（全类别召回）；geo 是精修、昂贵。先廉价保召回、后昂贵定位——与"安全非对称：漏是灾难"一致。

🌐 利用的天然约束

多视几何一致性（同物体在重叠视里 3D 须一致 → 去重/定深）；时序连续性（物体持存 → 时序传播/tracking）。

扎堆难点，在这套 L1 里不是"数量"

基数被可见性封顶（遮挡出 scope），固定 query 预算即够。真正的难点是 群内相互部分遮挡 / 可分辨性（以及部分可见个体要不要 amodal 补全）——这才是 per-view 检测 + 融合真正要扛的。

03

方案定稿 · 端到端管线

一句话本质：per-view 观测（可见性为根）→ 显著集自适应压缩（有界基数）→ 存在优先·geo 其次 → 跨 view/时序在定长 BEV 槽上关联去重 → 多模态补强；用有界 token 集 + SA 关联取代 dense grid + NMS。

01共享权重 backbone（view-兼容 CNN）L2
多相机 images → 每 view 各自出特征；权重共享，故 backbone 须兼容不同 view 下的物体检出。
↓
02per-view Perceiver · adaptive compressL1L2
view 特征 → 有界的显著物体 query 集。"像 mono3d 但不是 mono3d"：Perceiver 帮压缩+提取最显著物体 = mono 里做了 topk + group detection。基数有界是计算理论层的性质，非工程 hack。
↓
03两段头 · 存在-类别（what）→ geo（where）L1
先出检出信号（存在+类别），再 push query 从 mono3d 出发算3D 属性。存在优先=召回优先。
↓
04per-view temporal fusionL2
每 view 的 token 做时序稳定（抗闪烁），提升单 view 检出的时序一致性。
↓
05跨 view SA · 关联 + 压缩L2
把带 3D geo 的 perceiver token 做 self-attention，跨重叠视做关联与压缩（多视几何一致性）。
↓
06定长 N(~200) BEV unified token · 去重 + 关联 + 时序传播L2L3
一组定长 BEV unified token 与 perceiver token 做 SA（可与 05 联合一步做）完成去重+关联（slot-attention 味）；unified token 可从上一帧时序传入 → 4D tracking。定长 = 静态 shape = TRT 友好（早先担心的"固定 K"在这里翻转成优点）。
↓
07多模态 · unified token ←SA→ lidar/radarL2
~200 个 unified query 与 lidar/radar 做 SA 提信息。整套轻量，unified token 是接下游的干净接口 → 可升级 e2e。
04

L1 / L2 / L3 分析

把方案摆到三层上，逐层看它"要算什么/怎么表征算/怎么落地"。

L1 计算理论

  • per-view 为根：visibility 本质 per-camera，检测生于 per-view，世界模型从各视图证据拼装（Marr 自底向上）。
  • 存在→geo：召回关键量先算、精修量后算。
  • 基数有界：Perceiver 压出有界显著集（+group 处理簇）。
  • 持存在 scope：per-view token 稳定 + unified token 传播 = tracking。

L2 表征与算法

  • 表征：per-view Perceiver 物体 token；全局定长 N(~200) BEV unified token。
  • 算法：共享 backbone、Perceiver 交叉注意力压缩、两段头、per-view temporal、跨 view SA、unified SA 去重、时序传播、多模态 SA。
  • SA 关联取代 NMS；有界 token 取代 dense grid。

L3 实现

  • 轻量：有界 token→有界算力；共享 backbone→省显存；~200 token 上 SA→便宜。
  • 部署：定长 token = 静态 shape = TRT 友好；Perceiver 固定 query = 静态。
  • e2e 可升级：unified token = 接预测/规划的接口。
05

Polish · 设计决策 / 缺口 / 风险

把方案打磨到可实现：每条给出风险/缺口与推荐。粗体绿框为推荐决策。

P1单目深度歧义
per-view geo 深度病态；若各 view 先各自钉死 3D，深度误差在融合前 baked-in。
推荐：per-view 只出深度分布/不确定度，交给 unified 融合用多视几何定深。
P2group token 语义
"group detection" 须定义 token = 1 物体 还是 1 组；若为组，何时/是否解成个体。
推荐：group 作为可分辨性不足时的降级表示，可分则解成个体（扎堆=群内部分遮挡的落点）。
P3跨 view 关联正确性
unified token 抢 perceiver token 去重时的 split/merge 错误（同物→两 token，或两物→一 token）。
推荐：unified token 作竞争 slot；用几何一致性 + set loss 监督关联。
P4定长 N 容量
N(~200) 若小于极端稠密场景的可分辨物体数 → 饱和。
推荐：N 按 ego 范围最坏可分辨数定；birth/death + slot 回收做时序；饱和时退化到 group。
P5存在优先 & 全类别召回
类无关显著+后分类会让稀有类被常见类淹掉。
推荐：类条件 query 先验 + recall-first 损失，保稀有类召回。
P6两套 temporal
per-view（抗闪烁）与 unified（身份跟踪）职责需分清；unified 传播要处理自车运动。
推荐：unified 传播做 ego-motion 补偿；两套互补而非冗余。
P7监督设计
per-view 与 unified 两级的监督如何配合，避免早期 unified 学不到东西。
推荐：per-view mono3d 监督（存在/类别/geo）+ unified set loss（匈牙利或 slot）+ 时序一致性。
P8相关工作定位（诚实）
避免把已有范式当新意；需明确借鉴与差异。
定位：Perceiver-IO + DETR3D/PETR/Sparse4D（但那是 where-first BEV query）+ slot-attention + StreamPETR 时序 + MV2D "detect-in-view-then-fuse"。新意=per-view 自适应压缩前端(topk+group)+存在→geo 因子化+unified 4D token。
06

开放问题 / 下一步

L1 已闭合、L2/L3 方案已整理+分析+polish。进 L3 真代码前，待拍板的设计决策：

① group 语义
token = 物体 or 组？何时解成个体？降级策略的触发条件？
② 深度不确定度
per-view 出分布还是点估计？unified 处如何用多视几何定深？
③ 类条件先验
per-view Perceiver query 是否类条件化以保全类别召回？
④ N 与 birth/death
定长 N 取值 + 时序 slot 回收/新生机制？
⑤ 05/06 是否合一
跨 view SA 与 unified 去重是否联合一步 SA 完成？
⑥ 监督与 e2e 路径
两级监督配比；unified token 接下游 e2e 的时机？
下一步

从上述 ①②③ 先定关键决策 → 才进 L3 真代码。工程约束（TRT 定长、稀疏算子）确认可行后落地；训练必须实例化两段/融合的稀疏结构（train 一定 sparse），不在 dense ckpt 上推理期证伪。
