运营账

这套方案在计算收益时的主要问题，在于 hard case 无法快速迭代——技术方案缺点导致的接管次数、接管后 SD 遥操的控制时间长度和释放时机（配送任务中的人机比例问题），对应最终结果就是平均速度和单任务毛利。

团队管理账

VLA 方案跟 two-stage 方案对 infra 有着极其不同的需求；同时存在两个 team = 人员、算力和金钱上的冗余投入和浪费 + 非常严重的内部矛盾，而 data infra 和工程 team 没有冗余人力支持两代方案同时上线和迭代——这就是死局。

投入产出比

hard case 和必须要遥操的场景，受现有闭环效率以及方案限制，2-3 个 Q 之内几乎不会有什么大的改变；同期 VLA 方案本身的成本在大幅下降（早期 VLA 迭代只需要 10-15%）。

两代方案公平对比

大屏左右两栏；手机端自动上下堆叠：先完整读「现有方案」栏，再读「VLA 方案」栏，两栏用顶部色条区分。

先对齐定义（one-stage / two-stage）

  • 区分标准不是「是否带着感知一起训练」，而是：① 是否采用 pretrain-ft-posttrain 模式；② 是否去除感知任务作为上游任务的存在；③ 是否还需要在标注上花钱。
  • one-stage 中感知更多依赖预刷；预刷可以为 pretrain 提供所需要的感知标签，本质是对大模型的蒸馏；不需要精准的感知结果，因为下游没有依赖。
现有方案（perception+PnC → two-stage E2E）

成熟度

  • 现状基于 perception+PnC 模式；中间版本为无图和轻图版本，变量为是否添加 map 地图；沿此路线走到终态是 two-stage 的 E2E。
  • 数据闭环 infra、测试 infra、training infra、工程 infra 方案成熟；有成熟 team 可持续维护迭代。
  • 终态 two-stage E2E 可以解决大部分的非 corner-case 场景。

主要问题

  • 在计算收益时的主要问题，在于 hard case 无法快速迭代。
  • 明细：技术方案缺点导致的接管次数、接管之后 SD 遥操的控制时间长度和释放时机（配送任务中的人机比例问题），对应最终结果就是平均速度和单任务毛利。
VLA 方案
L4 行业现状
  • 除 Tesla 外没有人实际大规模部署上车。
  • Tesla 也就几百辆车；Waymo 有测试没有上路推送；Wayve 有测试但没有大规模部署，基本都不超过 50 辆的测试规模。
L2 收敛现状
  • 迭代方案和策略基本收敛；pretrain 跟随 LLM 发展，成本为早期 VLA 迭代的 10-15%；ft 及 post-train 策略方案趋近收敛。
  • 分歧点：各家 perception 和 pnc 部门的话语权 → ft/post-train 中感知数据、分析、pnc RL 策略比例变化。分歧不在技术，在于组织结构。

缺点与主要问题

  • 缺点在于黑盒以及迭代不可控，导致投入过多——想要一个全能的模型，但拿不到具体解决问题的结果。
  • 黑盒可以通过很多技术手段解决，现在已经不是主要问题了。
  • 目前的主要问题：持续迭代能力弱。根因是 data 和 test infra 要做大做全需要时间。
  • L2 参考：走得快的公司 infra 经过一年多的迭代第一版已经基本收敛了，但当初搓的缝合怪卡住了方案的持续迭代，亟待重构 infra。
