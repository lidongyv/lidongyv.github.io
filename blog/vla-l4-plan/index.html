02 · 两代方案对比

先对齐定义（VLA / two-stage）

区分标准不是「是否带着感知一起训练」，而是：

①是否采用 pretrain-ft-post_train 模式
②是否去除感知任务作为上游任务的存在
③是否还需要在感知标注上花钱
④是否按照感知场景集 × pnc 行为集的标签树进行数据闭环
VLA 中感知是作为 debug 辅助，而不是上游依赖任务，因此感知标注更多依赖预刷。

03 · 国内 robovan 现状

国内 robovan 现状

  1. 目前国内的 robovan 公司现状：有着比较成熟的 perception-pnc team，也可以根据运营的 issue 迭代。
  2. 各家的进度有所差距，主要体现在：是否完成了去 HDmap（无图），以及 是否有可迭代的数据闭环。
  3. 对于 e2e 方案，都属于在靠近 two-stage 方案的过程中，VLA 基本停留在口头。

去 HDmap（无图）

对 VLA：不是先决条件——map 作为多模态输入跟 lidar 一样，都是有就用的东西。
对 two-stage 方案是必须点——不是在技术上，而是在迭代效率上。
two-stage 方案不去掉 HD map 时的问题解决路径存在问题：
运营问题回流之后→ 必然有一大部分静态问题被分到 map，而不是 perception 或者 pnc 算路→ 组织上做了一个 shortcut：无法支持有用 issue 的回流入库和加入训练→ 长期 block 走向 two-stage E2E 的进度
临时方案和问题：
  • 1.在 pnc team 是组织核心时，可以靠人力密集完成一段时间的运营支持。
  • 2.将 HD map 加入 E2E 闭环会产生大量的数据鲜度问题以及版本管理问题
    这虽然是一个可以解决的问题，但是会耗费大量的研发精力，并且给数据闭环的存储和挖掘造成极大的难度

可迭代的数据闭环

能力要求

  • 这套东西有比较成熟的方案，前提是依赖上千辆人驾测试车的实测。
  • 回顾 two-stage 阶段：版本管理和问题回收账一直无法算清，OTA 更多依赖「更好」而不是「最好」的判断。

05 · VLA 算账的逻辑

VLA 算账的逻辑

第一个共识：遥操默认 AD 的平均速度为 0 →
无论使用何种方案，只要不需要人参与、可以继续开，就是正向的收益（短期对平均速度会有影响）。
VLA 替换遥操的第一步上限：遥操的均速控制 8-15 kph
0 8 15 20 kph
遥操默认 第一步上限 8-15 kph 后续
两套 issue 管理与算账模式
two-stage
  1. 根据现有测试标签体系，判定解决周期和投入
  2. 根据测试 issue 类型，建立 issue 管控和项目跟踪
  3. 主要跟踪的是对应 issue 标签消失的比例
  4. 项目核算对应 issue 对在途+两端成本核算的比例
VLA
  1. 根据遥操类型，重构标签体系
  2. 针对遥操代价和时间，划分标签价值
  3. 主要跟踪的是触发遥操后需要人驾参与的比例
  4. 项目核算触发遥操后需要人工参与的比例，计算降低人工的成本，以及是否产生额外的安全成本
冲突 issue 的处理
根据 issue 价值和解决周期进行 issue 归类，两个 team 不抢 issue，从成本和收益出发

落地节奏

先拿收益，不一把梭。
对于 L4 公司来说，首要的是拿到 VLA 的收益，而不是让 VLA 全面替代 two-stage。
第一目标：取得 VLA 的价值成果。
第一阶段
求同存异先拿收益
第二阶段
逐步变成万能的
第三阶段
通用 VLA 即是 WAM
第一阶段 · 求同存异先拿收益
two-stage 守基本盘（1-2 年）→ VLA 从遥操 / hard case 切入（8-15 kph 上限）→ 逐步扩大 VLA 边界，拿到价值成果
  • 1.1VLA 方案本身的成本在大幅下降 → 可以低成本跑通 VLA，先解决一部分 two-stage 不好解决的问题
  • 1.2我们不要一个大而全的 infra，对 robovan 来说再花两年重新迭代 infra 是不可接受的
    → 谋求跟现在 two-stage 方案共存，infra 有问题，但是又不是不能用
    → 借 VLA 开始迭代需要长时间积累的新 data 和 infra，并且磨合 team 转型
第二阶段 · VLA 不是万能的，但是也可以逐步变成万能的
榨干 two-stage→ 优化 VLA 成本和能力→ team 转型，交付 team 接力
  • 2.1跟随 L2 的算法迭代方向 → 逐步摸索方案上限和优化成本
    L4 有自己对算法的独特要求，不从零开始预研，就跟 VLA 使用 pretrain 而不是 from scratch 方法论上的统一
  • 2.2榨干 two-stage 的所有能力，当 two-stage 停止研发，只剩下数据迭代的时候
    让 two-stage 的 team 带着自己无法解决的问题，使用成熟的 VLA infra 进行新方案解决
    让功能负责人借助新算法，平滑拓展 VLA 的功能边界，让交付的人还是交付自己的功能
  • 2.3研发逐步建立 world model 以及独立的 pretrain vlm 能力，为大规模交付做好 infra 构建能力以及测试能力
第三阶段 · 通用 VLA 即是 WAM
robovan→ 在途场景的拓展→ 完善配送的最后 60m
  • 3.1从 robovan 到 robo truck，从 robovan 到 robotaxi
  • 3.2从 robovan 到配送的最后 60m
切记不能一把梭做 VLA
